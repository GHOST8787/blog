Claude Code 架構解構 (下)：
工程實踐、工具治理與驗證閉環

Engineering Tool Design Workflow
2026.04.03 BY GHOST_1010

接續上一篇確立的宏觀系統邊界與上下文規則後，本篇將視角轉向微觀的執行層面。我們將探討工具設計的核心原則、Subagents 的正確用法、高頻指令的工程意義，以及每個開發者都會經歷的三個演化階段。

工具設計：讓 Claude 少選錯

給 Agent 用的工具，和給人類呼叫的 API 有著本質的差異。人類追求「功能完整」，而 Agent 的設計重點在於 「降低誤判率」。

經典案例：AskUserQuestion 提問機制的演進史
  • V1
    Markdown 約定： 依靠提示詞要求特定格式提問
    Claude 經常忽視並強行輸出。
  • V2
    Flag 參數： 在既有工具中附加 --ask 參數
    參數常被略過。
  • V3
    獨立工具： 封裝為專屬的 AskUserQuestion Tool
    穩定可靠，調用即觸發系統中斷。
何時不該再加工具
  • 本地 Shell 已能可靠完成的事情
  • 模型只需要靜態知識，無需互動
  • 更適合放在 Skill 工作流約束的任務

Subagents：隔離比並行更重要

Subagent 的核心價值在於 「隔離污染」，而非單純的並行運算。例如掃描龐大代碼庫時，交給 Subagent 執行，主線程僅接收摘要，確保全局 Context 的純淨度。

配置時必須明確約束：
tools 限制能用什麼，別給全域權限
model 探索任務用 Haiku 省成本
maxTurns 設定步數上限，防止跑飛
worktree 需要動文件時隔離檔案系統

高頻指令的工程意義

這些指令的本質只有一件事：主動管理上下文，別等系統自己處理。

/insight

讓 Claude 提煉出「你們反覆提到但沒寫進契約的約定」，是迭代優化 CLAUDE.md 的最佳手段。

/rewind

回到特定的 checkpoint 重新摘要。當 Agent 路線嚴重偏移，或想保留前半段共識時的急救指令。

--fork

從當前上下文分支出平行宇宙，適合進行 A/B 架構設計比較，不污染原會話。

雙擊 ESC

回到上一條輸入重新編輯。Claude 走偏時，直接修改上一句話重發，比重新開會話快得多。

演化軌跡與驗證法則

1. ChatBot 階段

將其視為對話機器人，依賴人類大腦去補足缺失的脈絡。結果：上下文越來越亂。

2. 配置階段

開始撰寫 CLAUDE.md、添加外部工具。結果：規則越寫越長，模型開始選擇性忽略。

3. 工程化階段

焦點從「這功能怎麼用」轉變為「如何設計系統，讓 Agent 在約束下自主運作並自我驗證」。

驗證閉環：終極法則

「Claude 說完成了」絕對不等於完成。假如一個任務你無法明確定義 「跑完哪支腳本才算通過」，那它就不適合直接交給 Agent 自主執行。驗收標準必須在 Prompt 或 Skill 階段就徹底鎖死。
