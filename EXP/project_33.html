14 種圖與六種關聯線

工作上畫的架構圖與流程圖停在方塊與連線這一層：有哪些模組、誰連誰。兩個類別之間是繼承還是組合、一張訂單的狀態怎麼轉、前後端在時間軸上誰先呼叫誰，這些資訊在方塊圖裡沒有對應的符號可以表達。UML 2.0 把這些視角切成 14 種圖，每種管一件事。這篇把 14 種圖與六種關聯線各畫一張示意圖，最後附一張選圖對照表。

# UML 在做什麼

UML（Unified Modeling Language，統一塑模語言）是由 Object Management Group 維護的視覺化建模語言標準，用來描述軟體系統的結構與行為。現行版本是 UML 2.x，規範本體公開在 OMG 官網。

它處理兩件事。溝通：把程式邏輯與系統架構轉成有固定語彙的圖，開發者跟非技術的利害關係人看同一張圖得到同一個理解。藍圖：在寫程式之前先把類別、物件、流程規劃完，設計上的矛盾在編碼之前就攤開來。

固定語彙是整套東西的重點。自己畫的流程圖裡，一個方塊的意思由畫的人當場定義；UML 的每個符號在規範裡有明確語義——空心三角箭頭永遠是繼承，實心菱形永遠是組合，換一個人看得到同一個結論。

# 14 種圖怎麼分類

UML 2.0 定義 14 種圖，第一層切成結構圖 7 種與行為圖 7 種，行為圖裡有 4 種另外歸成互動圖子類。

分類依據是「這張圖在描述哪一面」。結構圖看系統靜止時長什麼樣：有哪些類別、模組怎麼切、元件跑在哪台機器上。行為圖看系統動起來做什麼：流程怎麼走、狀態怎麼變、使用者能操作什麼。互動圖專注在物件之間的訊息怎麼傳、按什麼順序傳。

# 讀圖之前：基本符號

14 種圖共用一套基本圖形語彙。類別畫成三格矩形：名稱、屬性、方法由上而下分區，每個成員前面用 + - # ~ 標示 public、private、protected、package 四種可見性。

物件實例沿用同一個造型，名稱加底線並寫成 實例名 : 類別名，屬性區填的是實際值。介面在名稱上方加 «interface» 標記，通常只有方法區。封裝畫成資料夾造型，左上角標籤放封裝名稱。

# 六種關聯線

類別圖的資訊量集中在線上。同樣是兩個方塊相連，線的樣式與端點符號決定它們是什麼關係，這六種關係在程式碼裡各自對應一種寫法。

繼承（泛化） Generalization

子類別取得父類別的所有屬性與方法，可以覆寫父類別的行為。程式碼層級是 Java 的 extends 或 C# 的 : 父類別。語義上子類別「是一種」父類別——貓是一種動物，貓繼承動物的 行走()、叫() 再改寫成自己的版本。單繼承語言裡一個類別只能繼承一個父類別。

實現 Realization

類別承諾實作介面定義的全部方法簽章，介面本身只規定「必須有哪些方法」。程式碼層級是 implements 或 : I介面名。介面規定 握手() 和 吃罐罐()，實作類別必須把兩個方法都寫出具體邏輯，少一個就編譯失敗。一個類別可以同時實現多個介面。

依賴 Dependency

A 的某個方法在執行期間臨時用到 B，A 本身沒有持有 B 的參考。B 透過方法參數、區域變數或回傳值短暫出現。Me.致富() 接收股票和彩券當參數，Me 類別內部沒有這兩個屬性欄位，方法結束關係就消失。六種裡耦合最弱的一種。

關聯 Association

A 的屬性欄位持有 B 的參考，B 從外部注入（建構子傳入或 setter 設定）。辣椒作物有一個天氣屬性，天氣物件在建構子裡從外部傳進來，成熟採收() 靠 this.天氣.目前季節() 取資訊。天氣的生命週期獨立於辣椒作物，天氣被刪除時辣椒作物還在。

聚合 Aggregation

整體持有部分的集合，部分可以脫離整體獨立存在。團體的成員屬性是 List<人>，人透過 加入團體() 從外部加入，也能退出。團體解散之後人還活著，同一個人可以同時屬於多個團體。畫法是空心菱形放在整體那一端。

組合 Composition

整體在建構時自己建立部分，部分的生命週期完全綁定整體。演員的建構子內部直接 new 墨西哥帽子() 和 new 棒球衣服()，帽子跟衣服由演員自己產生，演員被刪除時一起消失，也不會被其他整體共用。畫法是實心菱形放在整體那一端。

耦合強度由弱到強

依賴 → 關聯 → 聚合 → 組合 → 實現 → 繼承

實務上判斷只要問三題

  1. A 有沒有持有 B 的屬性欄位？
  2. B 是外部傳入的，還是 A 自己 new 出來的？
  3. A 消滅的時候 B 會不會跟著消滅？

# 結構圖（7 種）

1 — 類別圖 Class Diagram

標示每個類別的欄位、方法、可見性，以及類別之間的六種關聯線。UML 裡使用頻率最高的一張，設計模式的書幾乎都靠它表達結構。開發前用它確認物件關係，開發後它就是系統文件。

2 — 物件圖 Object Diagram

類別圖的快照版，顯示某個時間點下已經被 new 出來的實例各自持有什麼值。類別圖畫的是規格，物件圖畫的是某一刻的實際資料。用來驗證類別圖的設計在真實資料跑起來時站不站得住。

3 — 套件圖 Package Diagram

把類別、介面、子套件分組打包，用虛線箭頭標示模組之間的依賴方向。大型系統靠它確認模組切分合理、沒有循環依賴。

4 — 組件圖 Component Diagram

比套件圖粗一級，描述系統由哪些可獨立部署的單元組成。一個 .dll、一個微服務、一個 API 模組都算一個元件。元件之間用棒棒糖符號（提供介面）接半圓符號（需要介面），確認部署單元的邊界與介面契約。

5 — 佈署圖 Deployment Diagram

軟體元件實際跑在哪些硬體節點上，節點之間用什麼協定連線。節點是一台實體伺服器、一個 VM 或一個容器，元件放在節點內部，連線標上 HTTP、TCP、gRPC。跟維運團隊討論基礎架構時用這張。

6 — 剖面圖 Profile Diagram

對 UML 本身的語法做擴充，定義自訂的標記（Stereotype）、標籤值、約束，讓標準 UML 能描述特定領域的概念。例如定義一個 «RESTful» 標記套用在元件上，表示這個元件遵守 REST 規範。標準語彙不夠用的時候用它擴充。

7 — 複合結構圖 Composite Structure Diagram

打開一個類別或元件的內部，顯示它的零件怎麼透過連接埠與連接器接線。類別圖看的是類別之間的關係，複合結構圖看的是一個類別內部的組裝方式。嵌入式系統與硬體建模常用。

# 行為圖（3 種）

8 — 活動圖 Activity Diagram

一個流程從起點到終點經過哪些步驟，包含判斷分支、平行分叉與迴圈。菱形是判斷，對應程式的 if/else；粗黑橫線是 Fork 與 Join，表示平行處理。業務流程、工作流程、演算法步驟都用它，功能上覆蓋傳統流程圖。

9 — 狀態圖 State Machine Diagram

一個物件在生命週期裡會經過哪些狀態，以及什麼事件觸發狀態轉換。圓角矩形是狀態，箭頭上標觸發事件。狀態可以巢狀（一個狀態內部再細分）也可以併發（同時處於多個子狀態）。訂單狀態機、連線協定、UI 元件的互動狀態都靠它描述。

10 — 使用案例圖 Use Case Diagram

從使用者角度描述系統提供哪些功能、哪些角色能操作哪些功能。火柴人是演員，可以是人、外部系統或排程器；橢圓是一個使用案例；矩形框起系統邊界。需求分析階段跟客戶確認「系統要做什麼」用這張，內容完全不涉及怎麼做。

# 互動圖（4 種）

11 — 時序圖 Sequence Diagram

物件之間按時間順序傳遞訊息的過程。垂直軸是時間由上往下，水平軸是參與的物件，每個物件底下有一條生命線。實線箭頭是方法呼叫並標上方法名，虛線箭頭是回傳值。追一個操作從頭到尾經過哪些物件、呼叫哪些方法，這張最直接。

12 — 通訊圖 Communication Diagram

描述的事情跟時序圖一樣，改用空間佈局呈現。物件自由擺放，訊息標上巢狀編號（1、1.1、1.2、2）表示呼叫層級。時序圖強調先後順序，通訊圖強調誰跟誰有連線。物件多而互動順序單純的時候比時序圖好讀。

13 — 互動摘要圖 Interaction Overview Diagram

活動圖與時序圖的混合體。外層是活動圖的控制流程，每個節點裡面放一張小型互動圖，判斷分支決定走哪條路。一個完整流程包含多段不同的互動場景時，用它串起全貌。

14 — 時間圖 Timing Diagram

波形圖風格，橫軸是時間刻度，縱軸是狀態值。狀態圖畫狀態與轉換，時間圖多了每個狀態持續多久這層資訊，而且可以疊放多個物件的時間軸觀察同步狀況。即時系統與硬體協定的時序對齊靠這張檢查。

實務上 14 種圖不會全部用上。日常最常畫的是類別圖、活動圖、狀態圖、時序圖這四張，剩下十種按需要取用。先把六種關聯線的語義記熟，類別圖就讀得動，其他圖的符號再查規範補。
