公開許願板小工具：
Whiteboard

把只有自己看得到的待辦清單攤開，讓看的人投票決定順序

Engineering Firebase 工具實作
2026.09.25 BY GHOST_1010

想聊聊這個站上的許願板是怎麼來的：一開始的構想、架構怎麼切、中間卡在哪，還有為什麼它到現在還掛在那裡。

前情提要

寫程式對我來說是興趣。既然是興趣，只有自己在用就有點可惜，我希望它能發揮一點用途跟價值。另一件想要的事情是一個溝通的管道——來看這個站的人，總該有個地方能跟我說「這個我想看」。

所以有了 Whiteboard。2026-05-09 那個晚上先搭了一個空殼：hero、兩個區塊、右下角一顆按鈕、一個投稿視窗，什麼功能都還沒有。隔天一整天把核心功能全部補完。

# 一開始想做成什麼樣子

構想很單純：一面公開的牆，任何人登入都能貼一個想法上去，其他人按愛心決定它排多前面，我做掉的往下沉成一份可以回頭翻的紀錄。三個狀態、一條單向的路，沒有更多。

唯一要先想清楚的是灌水。驗證碼、速率限制、關鍵字過濾，這些各自能擋掉一部分，維護成本也跟著長出來，而這個站的流量規模用不到那一整套。所以我把它簡化成一句話：任何人都能送，公開與否由我審核決定。

# 架構：三個節點就是三個狀態

資料放在 Firebase Realtime Database，Google 代管、瀏覽器可以直接讀寫的資料庫，權限寫在它自己的 Security Rules 裡，逐個節點宣告誰能讀、誰能寫。這個站沒有後端，整套權限模型就靠這份檔案撐著。

第一版我想的是全部放在同一棵樹底下，用欄位把待審的內容遮起來。這條路走不通——讀取權限會往下傳，父節點一旦開放，底下全部跟著開放。於是改成三個獨立節點，審核這個動作就等於把資料從一個節點搬到下一個。

這樣切完之後，整套流程裡沒有一個叫做 status 的欄位要維護。待審區的讀取權限只認站長，所以送出去的東西在通過之前誰都看不到，連投稿的人自己也一樣。

# 工具本身怎麼設計

右下角固定一顆按鈕，點開填一行標題再選填幾句說明。兩個欄位都有長度上限，前端跟資料庫規則各檢查一次，前者擋手滑、後者擋繞過畫面直接打 API 的人。

愛心是一個帳號一票，再按一次收回。做法是兩個欄位配一條規則：一個存總票數，規則只准一次加一或減一；另一個按人分格，規則只准本人寫自己那一格。按下去的當下畫面先變，寫入失敗再把數字跟圖示回滾。

許願池的版面是 bento，卡片大小由票數決定：每跨過一個門檻就跳一級寬度，最低的一級佔四分之一排，最高票那張可以吃掉大半排、並且往下多佔一列高度，超過門檻之後另外加一層外框。整面牆會隨著大家按愛心慢慢變形，我這邊不需要維護一份排序設定。

最後是一個只有我看得到的審核頁。待審清單、通過、駁回、畢業四個動作，投稿者的聯絡信箱一路從待審帶到已實作，這樣要回信找得到人。

# 中間卡住的地方

登入壞掉，而且修了兩次

第一版用 Firebase 內建的彈窗登入。本機開 Live Server 一切正常，推上 GitHub Pages 之後彈窗關不掉，畫面只丟出一句「The requested action is invalid」，沒有堆疊也沒有錯誤碼。

原因是 COOP 這個標頭。它會切斷網頁與它開出來的視窗之間的引用關係、避免互相操控，GitHub Pages 預設就送。引用斷掉之後，彈窗完成登入沒辦法把結果傳回母頁面，也關不掉自己。

當天我先改成 redirect 把它繞過去，頁面整個跳走再跳回來，能動但體驗很差。真正的解法是三週後才換上的：用 Google Identity Services 在頁面內取得憑證，再在同一頁換成資料庫認得的身分，全程不開新視窗。

這條坑本機測不出來。線上跟本機送的標頭不同，等於兩個不同的執行環境。

兩條資料庫連線撞在一起

首頁的愛心按鈕早就開過一條 Firebase 連線，許願板的程式再開一次會撞名，因為預設連線同一個站只能有一個。解法是初始化的時候多帶一個名字，讓它變成一條獨立的具名連線，同一份設定、兩個互不干擾的實例。

# 做完了，也還在用

從 05-09 的空殼到 05-10 收工，核心功能是一天做完的；後來又補了英文版，六月把登入換成現在這套。它現在還掛在站上，我自己也還在用它記待辦，之後有想加的東西會繼續加。

第一次做這種對外開放投稿的東西，一定有沒想周全的地方。有建議的話直接在許願板貼一則最快，我看得到；想直接丟意見或看程式碼的話，站的原始碼全部公開在 GitHub，開 issue 或給一顆 star 我都收得到。

# 技術棧

  • 前端：原生 JavaScript ＋ Tailwind，單一檔案，無框架無打包工具
  • 部署：GitHub Pages
  • 資料庫與權限：Firebase Realtime Database ＋ Security Rules，站長身分靠比對一組固定帳號來判斷
  • 登入：Google Identity Services，頁內登入不開彈窗
  • 即時更新：監聽已公開與已實作兩個節點，資料一變畫面就跟著重畫
  • 票數：transaction 加減，另一個欄位按人分格記錄投過的人
  • 共用：跟 Meet 共用同一個 Firebase 專案與同一份權限檔，兩個工具各佔一個頂層節點
