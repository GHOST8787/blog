為 AI 搭一套擋幻覺的記憶系統
三道關卡，對照 GitHub 上一樣的回報

AI & Automation Memory System Claude Code
2026.06.25 BY GHOST_1010

生成式 AI 工具的可靠性問題，常見於未經查證的內容被當成事實輸出，例如生成不存在的數值或宣稱讀過未開啟的檔案。要把這類工具用於實際工作，需要在模型之外補上一層結構來攔截這種輸出。這篇記錄為日常使用的 Claude Code 建立的一套記憶與防護機制，並對照 2026 年 6 月 GitHub 上一批同類問題的回報。

# 它最常出包的三種狀況

先講三個實際遇到的情況。

一、資料還沒到，先給一個編的數字。我請它同時跑幾個背景搜尋，工具都還沒回傳，它就先丟出一個數字當結論。那個數字事後在任何一個搜尋的輸出裡都找不到，是在資料到齊之前自己補上去的。

二、沒去找，就說「找不到」。我要它確認一個之前存好的記憶檔還在不在，它沒有真的執行搜尋，直接回「不存在」。那個檔案就在原本的位置。

三、同一個被否決的做法，再提一次。一個先前已經否決掉的方案，它在沒翻記憶的情況下又重新提了出來。這種「沒查記憶就重講舊方案」的同款錯誤，累積下來有 19 次。

這些錯誤的共同點是語氣篤定且內容站不住，且表面上看起來正常，事後難以察覺。麻煩的地方就在這裡：它錯得很有自信。

一開始嘗試用規則攔截，但純文字規則的約束力有限，即使累積上百條，同類錯誤仍持續發生。規則只是「說明」，做不做仍由模型自己決定，中間缺了一個一定會擋下來的環節。

# 我的做法：在它出錯的那一刻擋下來

這套機制分三層，各自對應一種具體的失效形態。

  • 第一層，記憶：
    檔案式記憶，跨對話保存專案進度與既有決策，降低重複詢問與資訊遺失。每則事實獨立成檔，並附帶來源。
  • 第二層，強制檢查（閘）：
    將規則轉為動手前實際攔截的檢查：未查記憶不得修改、修改前須先輸出診斷、宣稱「找不到」或「不存在」前須先執行搜尋。其中「未查記憶即重提已否決方案」累積 19 次同類錯誤、「指令格式錯誤」累積 240 次，作為設置對應檢查的依據。
  • 第三層，心跳：
    檢查背景自動化是否還活著。有一次負責寫記憶的背景程式默默停掉，資料整段沒被寫進去，過了好一陣子才發現。因此加上心跳檢查：排程沒有如期執行時主動回報，不要等到事後才知道。

三層機制分別對應資訊遺失、重複錯誤與靜默失效，攔截點涵蓋四個條件：未查記憶、未輸出診斷、宣稱「找不到」前未搜尋，以及心跳未按時回報。任何一個條件成立，就在那一刻擋下來。

# 不只是我：GitHub 上一樣的狀況

2026 年 6 月，GitHub 的 Claude Code 專案出現一批集中回報，對象為 Opus 4.8。其中一則記錄模型在平行任務完成前就提交了捏造的數值，事後確認該數值不存在於任何工具輸出。官方對整體幻覺率的說明為各基準答錯率最低，達成方式是對不確定的問題選擇不作答；前述平行情境屬於此機制未涵蓋的部分。

其中一則回報是一位開發者的整理：使用檔案式記憶兩個月後歸納出的 5 種失敗模式。以下將該清單逐項對照本機制，其中 4 項已被涵蓋。

  • 規則僅為說明，需有強制環節才能攔截。
    實作：寫一支 PowerShell hook 掛在每次工具呼叫前（PreToolUse），內建 9 道檢查閘。例如「編輯檔案前必須先查過記憶」這條規則，hook 會檢查本次 session 有沒有讀過 memory 資料夾，沒有就直接擋掉，回傳 BLOCKED 訊息。規則寫在文件裡可以被忽略，寫進 hook 就是硬擋。
  • 未標來源的模型輸出，會被當成事實沿用。
    實作：記憶系統寫入任何外部事實時，必須附上可查證的來源（檔案路徑加行號、或 URL）。hook 本身沒辦法攔這條，所以改用規則搭配事後稽核——wrap 時的審計腳本會掃描最近寫入的記憶，標出沒有來源的條目。這是 5 項裡唯一靠規則守、沒有硬擋的。
  • 歷史紀錄與當前待辦狀態，須分開存放。
    實作：看板檔 TASKS.md 只放「現在要做的事」，完成的項目搬到 TASKS_archive.md。兩個檔案各管一件事，看板不堆流水帳，歷史不會因為看板清理而消失。
  • 缺少心跳的自動化，會靜默失效。
    實作：背景排程每隔固定時間回報一次狀態（類似伺服器的 health check）。如果超時沒回報，就知道哪個環節卡住或死掉了。用的是 Claude Code 內建的定時喚醒功能，設定間隔後它會自動回來檢查。
  • 兩個同名檔案，會產生內容漂移。
    實作：每份記憶檔的 frontmatter 裡有一個 last_updated 日期欄位，由寫入的那一刻蓋上。判斷哪份是最新的看這個日期，檔案系統的修改時間不算數（搬檔、同步都會改到它）。定期跑的審計腳本會比對日期，超過 60 天沒更新的記憶會被標記為可能過時。

5 項失敗模式中，已有機制涵蓋 4 項；第 2 項（未標來源的輸出被當成事實）則需依賴規則守住：寫入外部事實時一律附上來源。

幻覺的控制依賴模型外部的結構。模型自身行為是否改變非使用者可控，使用者能掌握的是錯誤輸出時是否有攔截點存在。一位獨立使用者在兩個月後歸納的失敗清單，與本機制的設計高度重疊，可作為這個方向的一個外部對照。
