AI 輔助開發的現實碰撞：
修復六年開源懸案的血淚與重構紀律

Open Source AI Agent Data Pipeline
2026.02.21 BY GHOST_1010

這是一場為期 48 小時的極限抗爭。最初介入 line-message-analyzer 開源專案，並非單純為了修復兩個擱置六年的歷史 Issue，而是基於我個人的四個戰略目標：

  • 驗證 VibeCoding 生態：親身體驗這半年來，純自然語言輔助開發的環境與工具鏈，是否已經具備真正的落地生產力。
  • Antigravity 協作實戰：實機演練如何與自主型 AI Agent 進行專案協作，並測試其邊界控制能力。
  • 開源社群探勘：本身對 line-message-analyzer 專案的應用場景抱有高度興趣，期望能解決社群長期的痛點。
  • 數據工程前置練兵：作為未來職涯走向數據領域的跳板，藉此專案完整走過一次「非結構化數據擷取、清洗、分析到圖表視覺化」的 Pipeline。

然而，這場原本計畫周密的練兵，最終卻演變成一場對抗真實數據混沌、與 AI Agent 失控行為博弈的深度重構之旅。

# 資料層的混沌：真實世界的邊界條件

專案的起手式很單純：解決 Issue #2（使用者名稱包含空格導致解析錯誤）與 Issue #4（英文 12 小時制 AM/PM 格式導致系統崩潰）。我原以為這只是幾行 Regex（正規表示式）的修正，但當我深入底層邏輯並撰寫測試案例時，才發現真實的 LINE 聊天匯出檔格式堪稱災難。

  • 日期格式的碎裂： 除了標準的 2026/02/21，還存在 2025.08.04 星期一 這種帶有特殊符號與後綴的格式。
  • 系統訊息的干擾： 傳送圖片、貼圖時沒有標準的括號包覆，甚至語音通話紀錄也只是一串純數字（如 00:17），缺乏明確的前綴識別。

這告訴我一個鐵律：永遠不要低估真實世界資料的複雜度。 依賴單一且脆弱的分隔符號（如空格）去解析非結構化文本，註定會在極端案例中全線崩潰。最終我選擇引入更嚴謹的 Tab 分隔符機制，並針對混合格式設計了壓力測試環境。

# AI Agent 的失控邊緣 (Antigravity 實戰)

為加速重構，我引入了 Antigravity 作為輔助開發工具，並透過自定義 Skills（line-parser-fix 與 generate-line-tests）來約束 AI 的行為。然而，這正是惡夢的開始。

AI 幻覺與過度干預的代價

當我讓 AI 根據 Skill 自動修改程式碼時，發生了典型的「黑箱災難」：

  1. 無中生有的功能： AI 自作聰明地加入沒人要求的「每日照片數量」圖表，甚至將搜尋結果的 X 軸強行改為「天數」而非「日期」。
  2. 毀滅性的 UI 覆寫： 圓角元件變成直角、Navbar 字體比例失衡、統計數字失去了千分位格式，甚至出現不明的「未知對象」標籤。
  3. 邏輯陷阱： 在處理「收回訊息」時，AI 錯誤使用了 continue 語句，導致後續的大量有效數據被直接跳過，資料統計全錯。

這讓我深刻體悟到：AI 是助手，不是神。 當你給出「幫我修復這個 Bug」這種模糊指令時，AI 為了展現其能力，往往會進行未經授權的全局改寫。陷入「修好 A 壞掉 B，修好 B 壞掉 C」的無窮迴圈，是因為我們將「架構控制權」讓渡給了不可控的 LLM 黑箱。

# 重塑工程紀律：血淚換來的 Best Practices

在經歷了數十次失敗、截了超過 15 張錯誤分析圖後，我強制終止了 AI 的全局操作，退回最根本的軟體工程紀律。這是我整理出的實戰法則：

1. 資料驗證先行 (TDD)

永遠不要在資料出錯時去改前端。我獨立抽出了 debug.js，在將資料丟給圖表或 DOM 之前，先在 Node.js 環境中確保陣列輸出 100% 正確。

2. 原子化 Commit

拒絕 AI 的大禮包式修改。一次只修復一個功能，確認無誤後立即 Git Commit。這是為了在 AI 突然「發瘋」改爛全域設定時，能以最低成本回溯。

3. 警惕工具盲區

Live Server 的快取機制會導致程式碼與畫面不對等；廢棄的 CSS 幽靈 Class 是萬惡之源。每次修改樣式後，強迫自己清理冗餘代碼並 Ctrl + F5 強制刷新。

4. 響應式與 Canvas

不能僅靠 vw 走天下，必須搭配 max-width 與嚴謹的 Media Query。同時，Canvas 的實體 width 屬性必須與 CSS 嚴格對齊，否則圖表標籤必定破版。

# 戰略覆盤：四項目標的殘酷解答

經歷這 48 小時的拉扯，回頭檢視最初設定的四項戰略目標，這是我得出的現實解答：

1. VibeCoding 生態驗證

結論：架構整齊度有餘，但微調決策仍高度依賴人腦。
無可否認，VibeCoding 確實在初期建構與維持程式碼的整齊度（Clean Code）上有著極佳的助益。然而，這個專案的 HTML 與 CSS 總行數不到 300 行，在如此輕量的架構下，面對細微排版與特定邏輯修復時，純自然語言開發的溝通與試錯成本甚至遠大於傳統的手刻編碼。這讓我確信：關於邏輯的「選擇、修改與微調」，目前依然只有人類的心智模型能夠精準辦到。

2. Antigravity 協作實戰

結論：架構掌控權不可讓渡。
隨著專案上下文的累積，AI Agent 在後期必然會出現「失憶與幻覺疊加」，開始無中生有或隨意竄改現有內容。在目前的 VibeCoding 模式下這幾乎是無解的。我認為未來的協作模式仍必須依賴「半人為介入」，由人類牢牢把控架構邊界。

3. 開源社群探勘

結論：順利達成基礎協作閉環。
成功練習了在 GitHub 上的開源貢獻流程，利用 Fork 功能將開源專案引入本地端進行分支修改，為日後更深度的社群協作打下基礎。

4. 數據工程前置練兵

結論：前端泥沼拖慢了進度，但確立了核心方向。
受限於前端修復的耗時，本次並未深入走到高階的分析與圖表視覺化階段。但這次的教訓讓我確信，未來若要執行「半 VibeCoding」模式，核心的「非結構化數據擷取與清洗 (Data Cleaning)」絕對會是我優先切入的重中之重。

階段性總結

截至凌晨 3 點，我成功重構了 AppState 狀態管理，確立了 debug.js 驗證機制，並初步掌握了 Antigravity Skills 的馴服技巧。雖然前端版面仍在重構階段（用通俗的話說：還是一坨屎），但底層的骨架與數據流已經徹底穩固。

為什麼不放棄？也許是因為不想讓一個掛了 6 年的 Issue 繼續躺在那裡，也許是因為這是我親手打造的數據 Pipeline，或者單純只是出於技術人的固執。不管怎樣，天亮後，重構繼續。
