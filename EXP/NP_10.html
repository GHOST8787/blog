為 AI 搭一套擋幻覺的記憶系統
三道關卡，對照 GitHub 上一樣的回報

AI & Automation Memory System Claude Code
2026.06.25 BY GHOST_1010

生成式 AI 工具常見的可靠性問題，是把未經查證的內容當成事實輸出：生成不存在的數值、宣稱讀過並未開啟的檔案。要把這類工具用於實際工作，需要在模型之外補上一層結構來攔截這種輸出。這篇記錄為日常使用的 Claude Code 建立的一套記憶與防護機制，並對照 2026 年 6 月 GitHub 上一批同類問題的回報。

# 它最常出包的三種狀況

先講三個實際遇到的情況。

一、資料還沒到，先給一個編的數字。我請它同時跑幾個背景搜尋，工具都還沒回傳，它就先丟出一個數字當結論。那個數字事後在任何一個搜尋的輸出裡都找不到，是在資料到齊之前自己補上去的。

二、沒去找，就說「找不到」。我要它確認一個之前存好的記憶檔還在不在，它沒有真的執行搜尋，直接回「不存在」。那個檔案就在原本的位置。

三、同一個被否決的做法，再提一次。一個先前已經否決掉的方案，它在沒翻記憶的情況下又重新提了出來。這種「沒查記憶就重講舊方案」的同款錯誤，累積下來有 19 次。

三件事的共同點是語氣都很篤定，內容卻站不住，而且讀起來順、看起來正常，事後要一眼抓到很難。麻煩的地方就在這裡：它錯得很有自信。

我一開始想靠寫規則擋。純文字規則的約束力有限，規則累積到上百條，同類錯誤照樣重複。規則只是「說明」，做不做仍由模型自己決定，中間缺了一個一定會擋下來的環節。

# 我的做法：在它出錯的那一刻擋下來

這套機制分三層，各自對應一種具體的失效形態。

  • 第一層，記憶：
    檔案式記憶，跨對話保存專案進度與既有決策，降低重複詢問與資訊遺失。每則事實獨立成檔，並附帶來源。
  • 第二層，強制檢查（閘）：
    將規則轉為動手前實際攔截的檢查：未查記憶不得修改、修改前須先輸出診斷、宣稱「找不到」或「不存在」前須先執行搜尋。其中「未查記憶即重提已否決方案」累積 19 次同類錯誤、「指令格式錯誤」累積 240 次，作為設置對應檢查的依據。
  • 第三層，心跳：
    檢查背景自動化是否還活著。有一次負責寫記憶的背景程式默默停掉，資料整段沒被寫進去，過了好一陣子才發現。因此加上心跳檢查：排程沒有如期執行時主動回報，不要等到事後才知道。

三層分別對應資訊遺失、重複錯誤、靜默失效。實際的攔截點是四個條件：沒先查記憶、沒先輸出診斷、宣稱「找不到」之前沒先搜尋、心跳沒按時回報。任何一個條件成立，就在那一刻擋下來。

# 不只是我：GitHub 上一樣的狀況

2026 年 6 月，GitHub 的 Claude Code 專案出現一批集中回報，對象為 Opus 4.8。其中一則記錄模型在平行任務完成前就提交了捏造的數值，事後確認該數值不存在於任何工具輸出。官方對整體幻覺率的說明為各基準答錯率最低，達成方式是對不確定的問題選擇不作答；前述平行情境屬於此機制未涵蓋的部分。

其中一則回報是一位開發者的整理：使用檔案式記憶兩個月後歸納出的 5 種失敗模式。以下將該清單逐項對照本機制，其中 4 項已被涵蓋。

  • 規則僅為說明，需有強制環節才能攔截。
    對應第二層的強制檢查。
  • 未標來源的模型輸出，會被當成事實沿用。
    本次補上的部分：規定記憶中任何外部事實須附來源連結，附不出來則不寫入。
  • 歷史紀錄與當前待辦狀態，須分開存放。
    對應做法：一套檔案保存歷史，另一套僅記錄當前待辦。
  • 缺少心跳的自動化，會靜默失效。
    對應第三層，近期補上。
  • 兩個同名檔案，會產生內容漂移。
    對應做法：狀態以進度日期為準，檔案修改時間僅供參考。

5 項中有 4 項由既有機制涵蓋；第 2 項（未標來源的輸出被當成事實）為本次補上的部分。此項屬於檔案式記憶較難以機制硬性攔截的一類，主要依靠「寫入外部事實時一律附上來源」這條規則。

幻覺的控制主要來自模型外部的結構。模型自身行為是否改變，不在使用者的可控範圍內；可控的部分，是在錯誤輸出產生的當下是否存在一個攔截點。一位獨立使用者在兩個月後歸納的失敗清單，與本機制的設計高度重疊，可作為這個方向的一個外部對照。
