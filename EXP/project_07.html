Claude Code 架構解構 (上)：
系統分層、上下文邊界與緩存機制

System Architecture Context Engineering Prompt Caching
2026.03.12 BY GHOST_1010

本篇整理自近半年深度使用 Claude Code 的踩坑經驗。剛開始容易將其視為 ChatBot，但很快會發現：上下文越來越亂、工具越來越多但效果變差、規則越長越不遵守。這並非 Prompt 的問題，而是系統架構設計的本質。要駕馭它，必須先理解其底層的「六層架構」與「上下文邊界」。

核心：底層運作與六層架構

Claude Code 的核心不是「回答」，而是一個反覆循環的代理過程：
收集上下文 → 採取行動 → 驗證結果 → [完成 or 回到收集]

卡住的地方幾乎從來不是模型不夠聰明，而是給了錯誤的上下文，或是缺乏驗證與撤回機制。理解系統，最好的方式是將其拆分為六層：

系統層次 職責與定義
Context (上下文) CLAUDE.md / rules / memory：告訴 Claude「是什麼」。
Action (動作能力) Tools / MCP：告訴 Claude「能做什麼」。
Methodology (方法論) Skills：按需載入的方法論，告訴 Claude「怎麼做」。
Control (控制層) Hooks：強制執行某些行為，不依賴 Claude 自己判斷。
Isolation (隔離層) Subagents：隔離情境的工作者，負責受控自治。
Verification (驗證閉環) Verifiers：讓輸出可驗、可回滾、可審計。

只強化其中一層，系統就會失衡：CLAUDE.md 寫太長會污染上下文；工具堆太多會導致選擇混亂；Subagents 到處開會導致狀態漂移。

概念邊界：MCP / Tools / Skills / Hooks

CLAUDE.md & rules

專案級的持久契約與路徑局部規範。

典型誤用：把所有團隊知識全塞進根目錄。

Tools & MCP

賦予 Claude 存取外部系統的能力。

典型誤用：接太多 Server 擠爆上下文。

Skills

按需加載的工作流程與方法包。

典型誤用：寫得像百科全書，缺乏執行邊界。

Hooks & Subagents

強制執行的攔截層與隔離上下文的工作單元。

典型誤用：用 Hook 取代模型判斷。

上下文工程：最核心的系統約束

多數人把上下文當作「容量問題」，但卡住通常是因為「太吵了」。200K 的上下文並非全部可用，MCP Server 的工具定義是最大的隱形殺手。

建議的上下文分層策略：
始終常駐   → CLAUDE.md (專案契約 / 構建命令 / 禁止事項)
按路徑加載 → rules (語言 / 目錄 / 檔案類型特定規則)
按需加載   → Skills (工作流 / 領域知識)
隔離加載   → Subagents (大量探索 / 並行研究)
不進上下文 → Hooks (確定性腳本 / 審計 / 阻斷)
壓縮機制的陷阱與 HANDOFF.md

預設的壓縮演算法會優先刪除早期的 Tool Output 和檔案內容，順帶把架構決策和約束理由也一起丟了。

  • 在 CLAUDE.md 明確寫入 Compact Instructions（規定壓縮時必須保留架構決策、修改檔案等）。
  • 更主動的方案：切換複雜會話前，讓 Claude 寫一份 HANDOFF.md（記錄進展、走通的路、死路與下一步）。新實例只需讀取此檔案即可無縫接軌。

Prompt Caching：內部架構的核心

Claude Code 的整個架構都圍繞著 Prompt 緩存構建。高命中率不僅降低成本，也影響速率限制。緩存是按前綴匹配工作的，因此順序極為關鍵：

1. System Prompt (靜態) → 2. Tool Definitions (靜態) → 3. Chat History (動態) → 4. User Input (最後)
破壞緩存的常見陷阱：
  • 在系統 Prompt 中放入動態內容（如時間戳）。動態資訊應透過 <system-reminder> 標籤放在用戶訊息中。
  • 會話中途增刪工具，或非確定性地打亂工具定義順序。
  • 中途切換模型： Prompt 緩存是綁定模型的。從 Opus 切換到 Haiku 需要重建整個緩存，反而更貴。應透過 Subagent 交接任務。
