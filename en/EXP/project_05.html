Building an AI Customer Service Automation:
Integrating Make, an LLM, and a Knowledge Base

AI & Automation Workflow Automation LLM Application
2026.02.20 BY GHOST_1010

Running a physical retail business means high-volume, repetitive customer inquiries. Handling them with people burns hours. The usual rule-based bot has no semantic understanding and falls over on anything off-script. To free up staff while keeping service quality stable, I built an automation on Make that wires together LINE Messaging API, Google Workspace, and an LLM — with intent recognition and retrieval-augmented generation (RAG) built in.

Heya

Built for a brick-and-mortar retail client's LINE Official Account smart support. When a customer asks a question on LINE, the backend routes it automatically: common questions (product specs, warranty, purchase flow) get an AI-generated answer drawn from the company's existing knowledge base; cases needing a human get forwarded to live support. The whole system is wired through Make (a drag-and-drop automation platform, similar to Zapier), connecting LINE API, Google Docs, and the AI model without any low-level code. RAG (retrieval-augmented generation) means the AI looks up company documents before answering, grounding its responses in retrieved content rather than making things up.

# System Goals and Architecture

The goal: an extensible automated triage system. Concrete requirements broken into modules:

  • Intent recognition and routing: auto-detect user intent, separate routine technical questions from cases that need a human.
  • RAG implementation: based on question category, dynamically pull external domain knowledge (Google Docs) as grounding for the LLM. Cuts hallucination.
  • State tracking and context: a user entity database that records interaction history, so the conversation has continuity.
  • Escalation: when the input crosses the AI's boundary, fire a notification channel to a human agent.

# Workflow Design

Inside Make's visual editor, I broke the business logic into independent nodes. Each module passes a standardized data shape to the next, so coupling stays low:

1. Identity check and DB init

Webhook fires. The HTTP module calls LINE API and pulls userId as the primary key.
Then a lookup in the data store: new user, run init and create a record. Returning user, load the conversation history array as LLM context.

2. Node one: intent recognition and routing

A dedicated prompt configures the first LLM as an intent classifier.
After feature extraction, it decides whether the user is asking for a human. The model is forced to output a boolean — that boolean acts as the router that splits the downstream path.

3. Node two: domain classification and retrieval

Routine questions flow into the second tier. A second LLM splits them into "B2C sales" or "technical support."
Based on that label, the system points to a specific Google Doc, pulls the relevant text, and stages the data for retrieval-augmented generation.

4. Node three: final LLM reply

The system merges the raw question, prior context, and retrieved knowledge into the final prompt.
• Constrained generation: force the LLM to answer from the retrieved text, no drifting.
• Compliance: the base layer auto-attaches a medical disclaimer where needed.
• State write-back: the Q&A is persisted to the database, closing the session cycle.

5. Node four: human-in-the-loop

If node one trips the human-intervention flag, the system short-circuits generation and sends the client a holding message.
At the same time, it packages the raw input plus user UID and pushes through a separate API channel to the admin side. The case lands on a real person with zero delay.

# Results After Launch

Operational metrics moved in concrete ways once the system went live:

  • Latency drops sharply: the system intercepts over 90% of L1 routine inquiries. Average response time goes from hours (human) to seconds (inference).
  • 24/7 coverage: async response runs around the clock. The off-hours service gap disappears.
  • Reallocated headcount: human attention moves off low-dimension repetition, onto high-complexity issues and core business work.

# Reflection and Extensibility

This project proved Make's strength as an API orchestrator in a modern stack:

  1. Low coupling: the visual flow keeps inter-module dependencies thin. Swap the underlying LLM or knowledge source without touching the rest.
  2. Cheap iteration: tuning AI output rarely needs code changes. Adjust the prompt at the relevant node and the system converges.
  3. Domain adaptability: without the compute to fine-tune a model, strict prompt engineering plus RAG can still get a general-purpose LLM to perform on a specialized vertical.

The same workflow generalizes well. Swap the retrieval source and rewrite the role boundaries, and it ports cleanly to any business with high-volume, unstructured questions.
