UML study notes
14 diagrams and six relationship types

Engineering System Design Reference
2026.10.03 BY GHOST_1010

The architecture and flow diagrams I draw at work stop at boxes and lines: which modules exist, what connects to what. Whether two classes sit in an inheritance or a composition relationship, how an order moves between states, which side calls which first along a timeline — a box diagram has no symbol for any of that. UML 2.0 cuts those views into 14 diagrams, one concern each. This piece draws all 14 plus the six relationship types, and ends with a table for picking one.

# What UML is for

UML (Unified Modeling Language) is the visual modelling standard maintained by the Object Management Group, used to describe the structure and behaviour of software systems. The current line is UML 2.x and the specification itself is public on the OMG site.

It covers two jobs. Communication: turn program logic and system architecture into a picture with a fixed vocabulary, so a developer and a non-technical stakeholder read the same diagram and come away with the same understanding. Blueprint: settle classes, objects and flows before any code exists, which brings design contradictions into the open ahead of implementation.

The fixed vocabulary carries the weight. In a hand-drawn flowchart, a box means whatever the person drawing it decided at the time. Every UML symbol has a defined meaning in the spec — a hollow triangle arrowhead is always generalization, a filled diamond is always composition, and the next person to read it arrives at the same conclusion.

# How the 14 diagrams are grouped

UML 2.0 defines 14 diagrams, split at the top level into seven structural and seven behavioural, with four of the behavioural ones further grouped as interaction diagrams.

The split follows what a diagram is describing. Structural diagrams show the system at rest: which classes exist, how modules are divided, which machine a component runs on. Behavioural diagrams show the system in motion: how a flow proceeds, how states change, what a user can do. Interaction diagrams focus on the messages objects send each other and the order they travel in.

# Before reading any of them: the notation

All 14 share one basic vocabulary of shapes. A class is a three-compartment rectangle — name, attributes, methods from top to bottom — with each member prefixed by + - # ~ for public, private, protected and package visibility.

An object instance reuses the same shape with the name underlined and written as instance : Class, and the attribute compartment holds actual values. An interface carries an «interface» marker above its name and usually shows methods only. A package is drawn as a folder with its name on the top-left tab.

# The six relationship types

In a class diagram the information lives on the lines. Two boxes are joined the same way every time; the line style and the endpoint symbol decide what the relationship is, and each of the six maps to a specific shape in code.

Generalization

A subclass takes on every attribute and method of its parent and may override the parent’s behaviour. In code that is Java’s extends or C#’s : Parent. The semantics are “is a kind of” — a cat is a kind of animal, inheriting Walk() and Speak() and rewriting them with its own version. In a single-inheritance language a class has exactly one parent.

Realization

A class commits to implementing every method signature an interface declares, while the interface itself only states which methods must exist. In code that is implements or : IName. If the interface declares Shake() and Feed(), the implementing class has to supply concrete logic for both, and leaving one out fails compilation. A class can realize several interfaces at once.

Dependency

A reaches for B during the execution of a method while holding no reference to it. B shows up briefly as a parameter, a local variable or a return value. Me.GetRich() takes a stock and a lottery ticket as arguments, the Me class has no fields for either, and the relationship disappears when the method returns. The loosest coupling of the six.

Association

A holds a reference to B in a field, injected from outside through a constructor or a setter. A chilli crop has a weather field, the weather object arrives through the constructor, and Harvest() reads from it via this.weather.season(). The weather object has a lifetime of its own, and deleting it leaves the crop standing.

Aggregation

The whole holds a collection of parts, and a part survives on its own. A group keeps its members in a List<Person>; a person joins through Join() from outside and can leave again. Disband the group and the people are still alive, and one person can belong to several groups at once. Drawn with a hollow diamond at the whole end.

Composition

The whole builds its parts during construction, and their lifetime is bound to it entirely. An actor’s constructor runs new SombreroHat() and new BaseballShirt() directly, so the hat and the shirt come from the actor, vanish when the actor is deleted, and are never shared with another whole. Drawn with a filled diamond at the whole end.

Coupling, loosest to tightest

dependency → association → aggregation → composition → realization → generalization

Three questions settle it in practice

  1. Does A hold B in a field?
  2. Is B passed in from outside, or does A new it up itself?
  3. When A is destroyed, does B go with it?

# Structural diagrams (7)

1 — Class diagram

Shows each class with its fields, methods and visibility, plus the six relationship types between them. The most used diagram in UML, and the one design-pattern books lean on to express structure. Before writing code it settles how objects relate; afterwards it serves as the system documentation.

2 — Object diagram

A snapshot of a class diagram, showing the instances that have been new-ed up at one moment and the values each holds. A class diagram draws the specification; an object diagram draws the data at a point in time. It is how you check that a design still makes sense once real data flows through it.

3 — Package diagram

Groups classes, interfaces and sub-packages into modules, with dashed arrows marking which module depends on which. Large systems use it to confirm the module split holds up and that no dependency cycle exists.

4 — Component diagram

One level coarser than a package diagram, describing which independently deployable units make up the system. A .dll, a microservice and an API module each count as a component. Components connect through a lollipop symbol (provided interface) meeting a socket symbol (required interface), which pins down deployment boundaries and interface contracts.

5 — Deployment diagram

Which hardware nodes the software components actually run on, and what protocol links those nodes. A node is a physical server, a VM or a container; components sit inside nodes and the connections are labelled HTTP, TCP or gRPC. This is the one to bring to a conversation with the ops team.

6 — Profile diagram

Extends UML’s own syntax by defining custom stereotypes, tagged values and constraints, so standard UML can describe concepts from a particular domain. Define a «RESTful» stereotype, apply it to a component, and the component now declares REST compliance. Reach for it when the standard vocabulary runs out.

7 — Composite structure diagram

Opens up a class or component to show how its internal parts wire together through ports and connectors. A class diagram looks at relationships between classes; a composite structure diagram looks at the assembly inside one. Common in embedded and hardware modelling.

# Behavioural diagrams (3)

8 — Activity diagram

The steps a flow passes through from start to finish, including decisions, parallel forks and loops. A diamond is a decision, matching an if/else in code; a thick horizontal bar is a fork or join for parallel work. Business processes, workflows and algorithm steps all use it, and it covers what a traditional flowchart does.

9 — State machine diagram

The states an object passes through over its lifetime and the events that trigger each transition. A rounded rectangle is a state and the label on an arrow is the trigger. States nest (a state subdivided internally) and run concurrently (several sub-states at once). Order state machines, connection protocols and UI interaction states all live here.

10 — Use case diagram

What the system offers, seen from the user’s side, and which roles can reach which features. A stick figure is an actor, which can be a person, an external system or a scheduler; an ellipse is a use case; a rectangle frames the system boundary. Requirements work uses it to agree with a client on what the system does, staying clear of how.

# Interaction diagrams (4)

11 — Sequence diagram

Messages passing between objects in time order. The vertical axis is time running downward, the horizontal axis holds the participants, and each one drops a lifeline. A solid arrow is a method call labelled with its name; a dashed arrow is a return value. For tracing one operation end to end through the objects and calls it touches, this is the most direct view.

12 — Communication diagram

Describes the same thing as a sequence diagram, laid out in space instead. Objects sit freely and messages carry nested numbers (1, 1.1, 1.2, 2) to show the call hierarchy. A sequence diagram emphasises order; a communication diagram emphasises who is wired to whom. With many objects and a simple order, it reads better.

13 — Interaction overview diagram

A hybrid of activity and sequence diagrams. The outer layer is activity-diagram control flow, each node contains a small interaction diagram, and the decisions pick which path runs. Use it to string together a full flow made of several distinct interaction scenes.

14 — Timing diagram

A waveform view with time on the horizontal axis and state values on the vertical one. A state diagram draws states and transitions; a timing diagram adds how long each state lasts, and several objects can be stacked to watch whether their timelines line up. Real-time systems and hardware protocols use it to check timing alignment.

In practice all 14 rarely come out. The four that get drawn regularly are class, activity, state machine and sequence, with the remaining ten available when the situation calls for one. Learn the semantics of the six relationship types first and a class diagram becomes readable; the symbols in the other diagrams can be looked up in the spec as needed.
