Deploying an AI Assistant Framework (Part 1):
Infrastructure and Daemonized Services

Engineering Cloud Infrastructure Deployment
2026.02.19 BY GHOST_1010

A log of deploying the AI agent framework (Clawdbot) on a cloud VM. Part 1 focuses on infrastructure: environment setup, daemonized services, and a secure tunnel to the control dashboard. The goal is a 24/7 AI service node I can reach remotely.

# Stage 1: Prerequisites

For Clawdbot to run on dedicated, stable compute, the setup needs these physical and network pieces in place:

  • Compute node (Cloud VM): a cloud VM with a public IP. I used an Azure VM running Ubuntu.
  • Security credentials: an SSH private key (<YOUR_KEY.pem>) for asymmetric auth.
  • Local control: a workstation with PowerShell or a comparable CLI terminal already set up.

# Stage 2: Secure Connection (SSH)

Password login is disabled for security. From your local terminal, switch to the directory holding the key and SSH into the remote Ubuntu server:

cd <YOUR_LOCAL_KEY_PATH>
ssh -i <YOUR_KEY.pem> <YOUR_VM_USER>@<YOUR_VM_IP>

# Stage 3: Core Service Setup and Daemonization

Install the framework via npm. To keep the AI agent process alive after the terminal session ends, register it as a systemd user service:

# 1. Global install
sudo npm install -g clawdbot@latest

# 2. Verify dependencies and version
clawdbot --version

# 3. Create and start the Systemd User Service
clawdbot gateway setup --user
systemctl --user start clawdbot-gateway.service

# 4. Check service status (should read active (running))
systemctl --user status clawdbot-gateway.service

# Stage 4: Edge Case — Port Conflict Resolution

Across repeated deploys and restarts, the service occasionally refused to start. Reading the system logs, the error code Port 18789 is already in use meant a zombie process or stale instance was holding the port. Force-cleanup procedure:

# 1. Stop and unload all related services and leftover unit files
systemctl --user stop clawdbot-gateway.service
systemctl --user stop openclaw-gateway.service 2>/dev/null
systemctl --user disable openclaw-gateway.service 2>/dev/null
rm -f ~/.config/systemd/user/openclaw-gateway.service

# 2. Free the port: kill -9 anything still holding 18789
sudo kill -9 $(sudo lsof -t -i:18789) 2>/dev/null

# 3. Reload the daemon and restart the cleaned service
systemctl --user daemon-reload
systemctl --user reset-failed clawdbot-gateway.service
systemctl --user start clawdbot-gateway.service

# Stage 5: SSH Tunneling and Dashboard Access

For security, Clawdbot Gateway binds to localhost on the server. Opening the firewall to the outside world directly would be a serious hole. The cleaner move: SSH tunneling (port forwarding). From a second local terminal, build an encrypted tunnel and map the remote 18789 port to your local machine:

ssh -i <YOUR_KEY.pem> -N -L 18789:127.0.0.1:18789 <YOUR_VM_USER>@<YOUR_VM_IP>

Back on the VM terminal, grab the dashboard URL and auth token:

clawdbot dashboard

Copy the URL, swap 127.0.0.1 for localhost, and open it in your local browser. If the token gets rejected, force-overwrite it via CLI: clawdbot config set gateway.auth.token <TOKEN>.

# Stage Validation

With the lower layer wired up and the service running as a daemon, I hooked Clawdbot to the Telegram API for an endpoint test. Message round-trip and AI agent responses both came through clean. Infrastructure layer is done. Higher-level intent logic can stack on top of this.
