NTUST Information-Security Architecture Project:
Letting AI Handle Customer Emails Without Seeing One Person's Real Personal Data

AI & Automation PII De-identification Security
2026.04 — 2026.06 BY GHOST_1010

An information-security architecture project from the AI course at National Taiwan University of Science and Technology. The brief: build an automated pipeline for customer emails that reads an incoming message, hands it to AI to draft a reply, and sends it back to the customer. The hard part is that incoming emails are packed with real personal data (name, phone, address, credit card number), and once that data reaches a cloud AI model it counts as a leak. The core of the whole system: AI only ever sees codes, and never sees any single person's real name and numbers.

Context

A real customer email looks like this: "I'm Wang Da-ming, mobile 0912-345-678, the thing I bought on your site last week still hasn't arrived." To ask AI to help write a reply, you have to feed the whole email to the model. The problem: the model runs in the cloud, and the moment this email is sent out, Wang Da-ming's name and mobile leave the range the company can control. The approach in this project: before sending, swap "Wang Da-ming" for USER_48213 and the mobile for PHONE_90577. AI sees the coded email and writes a coded reply, and at the company's end the codes get swapped back to the real names before the message goes to the customer.

# Task Spec

  • Input — a 500-row table of customer emails, each row with 7 columns (id, name, phone, address, credit card number, category, email body), where the body is free text and personal data is scattered across the sentences.
  • Processing — for each email: de-identify → hand to AI for a reply draft → verify the codes are intact → restore the real personal data → enter supervisor review → send after approval.
  • Output — an Excel report with three worksheets (processing results, code lookup table, batch info), for the supervisor to review row by row and decide which ones can be sent.
  • Security floor — the AI side only ever touches codes; real personal data lives only in the company's local lookup table and the restored report, both of which are kept out of the version control repo.

# Core Flow: A Four-Stage Pipeline

Stages 1 & 2

Read + De-identify

Read the emails from Excel, scan out the four sensitive columns, replace each with a code, and record "code → real value" in a lookup table. AI receives only the coded body.

Stages 3 & 4

AI Generation + Verify and Restore

AI reads the coded email and writes a coded reply. The system checks whether the code format and origin in the reply are valid, and only then uses the lookup table to swap codes back to real values and hand off to the supervisor.

Each of the four sensitive columns has a fixed code prefix, so the supervisor knows at a glance what type of data has been masked:

Column Code Prefix Example
NameUSER_USER_48213
PhonePHONE_PHONE_90577
AddressADDR_ADDR_31408
Credit card numberCARD_CARD_76652

# Two Code Strategies: Legacy and HMAC

The system offers two ways to generate codes. Legacy mode uses "prefix + five digits" as the code, readable and easy to match during a demo. HMAC mode hashes the real value through HMAC-SHA256 and takes a hexadecimal string, to guard against dictionary reversal.

Strategy Design
Legacy PREFIX_#####, a five-digit random integer. High readability, suited to demos and supervisor cross-checking.
HMAC PREFIX_XXXXXX, six hex digits taken from HMAC-SHA256(key, real value ‖ batch salt), a 16⁶ space. The key is at least 32 characters, and different salts isolate one batch from another.
Why HMAC + Batch Salt

A purely random code blocks "guessing the real value from the code," and leaves open the correlation analysis that comes from "the same value producing the same code every time." HMAC binds the key into the hash, so without the key an outsider cannot reverse it; the batch salt gives the same record a different code across batches, so cross-batch alignment fails. The key and the restored personal data both sit in the local .env and reports/, held outside the version control repo by .gitignore.

# Cross-Batch Isolation

The isolation unit for codes is the "batch." The system processes emails in batches by category, and each batch generates codes with its own independent salt. The same value gets a different code in a different batch, so cross-batch alignment fails; the same customer keeps the same code within one batch, which makes it easy for the supervisor to identify the same person inside that batch. Even if one batch's lookup table leaks, it cannot decode the same person's identity in other batches.

# Verification Loop and Manual Queue

The reply AI generates passes through a code verification step. The verifier first runs a strict format check (the rule is ^[A-Z]+_[0-9]{5}$, in plain words "uppercase letters + underscore + five digits," for example USER_48213), catching codes that break the format; it then compares against the lookup table, catching any code that is absent from the table and of unknown origin.

When verification fails, the pipeline sends the same row back to AI to regenerate, up to three times. A row that still fails after three tries gets marked MANUAL_REVIEW and pushed into the manual queue (FR-23) for a person to look at. This retry logic lives in the pipeline and uses rules to decide whether to retry, while AI handles only the generation of the reply content itself.

# A Second Line of Defense for Residual Personal Data

The first layer's column replacement handles the personal data in table columns. The email body is free text, and personal data can hide inside sentences too (for example a customer casually mentioning a third party's name and phone). pii_detector.py uses a set of regexes as a second line of defense, scanning for suspected personal data still left after de-identification, tagging it with an AUTO_ prefix for human review. Positioning detection as a second-layer safeguard and column replacement as the main capability was an architecture decision set during this project's April 2026 hardening phase.

# Engineering Hardening Added Before the Demo

  • Email defaults to dry-run — mailer.py defaults to not actually sending; you add --real to send for real. The SMTP connection adds timeout=10 to keep the demo from hanging on an unreachable mail host.
  • Encoding tolerance on read — data_loader.py tries utf-8 / utf-8-sig / big5 / cp950 in order, handling the Chinese Excel encoding differences common in Taiwan.
  • Two-stage approval — the AI draft enters the report and waits for supervisor approval; send_approved.py only reads rows marked APPROVED in the report to send, splitting "generate" and "send" into two steps that each need a human nod.
  • Real / simulated toggle — ai_client.py uses a switch to flip between the real API and simulated output, so the full pipeline can run for testing even with no key; the system prompt explicitly states codes must not be guessed.
