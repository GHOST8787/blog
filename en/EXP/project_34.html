LINE Desktop could not send images or files
IPv4, IPv6, and a hotspot whose IPv6 went nowhere

The phone hotspot handed out IPv6 addresses that could not reach the internet, so LINE Desktop stalled on images and files; with IPv6 turned off on Wi-Fi, connecting to LINE dropped from 106 seconds to 1.2.

Engineering Network Debug
2026.11.17 BY GHOST_1010

With the laptop on a phone hotspot, LINE Desktop sent text messages fine, while images and files spun forever. The hotspot handed out IPv6 addresses, but IPv6 could not reach anything outside, so every new LINE connection waited on IPv6 until it timed out before falling back to IPv4. After turning off IPv6 on the Wi-Fi adapter, connecting to the LINE server went from 106 seconds to 1.2.

# Symptom

LINE opened normally, chats and history loaded, and typed messages went out. Only images and files stalled on a spinner after pressing send. At the same time the browser loaded pages and played video without trouble, Wi-Fi showed connected, and both the gateway and a public DNS server answered.

The first move was a web search. Most answers said the same thing: update LINE.

# How I narrowed it down

LINE's update log already showed the latest version, 26.6.0.4004, so updating led nowhere. From there I went down one layer at a time, and each result decided what to check next.

# IPv4 and IPv6

Every device on a network needs an address so packets know where to go. IPv4 has been in use for more than forty years. Its addresses are 32 bits long, written as four numbers like 203.0.113.25, about 4.3 billion in total. Connected devices outgrew that long ago, and IANA, which hands out address blocks, allocated the last IPv4 blocks in February 2011.

IPv6 is the successor. Addresses are 128 bits, written in colon-separated hex like 2001:db8::1, enough for every device to have its own public address.

Address length32 bits128 bits
Written as203.0.113.252001:db8::1
Number of addresses232, about 4.3 × 1092128, about 3.4 × 1038
Default precedence (RFC 6724)3540
DNS recordAAAAA

The two live side by side. A computer can hold IPv4 and IPv6 addresses at once, and a domain can publish both. Before connecting, a program asks DNS, DNS returns both kinds, and the operating system decides the order.

Side note: why the computer tries IPv6 first

The ordering rules live in RFC 6724, which defines a precedence table; higher numbers go first. Ordinary IPv6 addresses (::/0 in the table) get 40, IPv4 addresses (::ffff:0:0/96) get 35, so IPv6 comes first. On Windows, netsh interface ipv6 show prefixpolicies prints the local copy of this table, with the same numbers as the RFC.

The table looks only at the kind of address, never at whether the path works right now. As soon as the computer holds a normal-looking public IPv6 address, it treats IPv6 as usable and tries it first. That is exactly where the hotspot went wrong: address assigned, route assigned, everything valid on paper, and no packet getting out.

Side note: why IPv4 still works after running out

NAT (network address translation). A home router gets a single public IPv4 address from the ISP; the phones, laptops, and TVs inside each get a private address like 192.168.x.x. Outgoing traffic is rewritten to the one public address, and replies are mapped back to the right device. Mobile data works the same way, with the carrier adding another layer so many phones share one public address. That keeps IPv4 alive, at the cost of devices not being able to reach each other directly without the router in between. IPv6 has enough addresses for every device to get its own, so this layer is unnecessary.

# Root cause: IPv6 with an address and no way out

The hotspot was a Galaxy A22 5G. It could hand out IPv6 addresses but had no working IPv6 path to the outside. LINE followed the ordering and tried IPv6 first. Get-NetTCPConnection showed two connections stuck in SynSent: the connection request went out and nothing came back. One pointed at LINE's own 2400:dcc0:a3a1:1000::5, the other at AWS CloudFront. LINE also had a connection already established over IPv4; text messages used that one, so they went through. Images and files need new connections, those tried IPv6 first, and they sat on these two.

Windows tries addresses one at a time and waits for each to time out before moving on; IPv4 only gets its turn after every IPv6 address has failed. That is how the 106 seconds in step 1 of the chart added up. The connection test reported success in the end, so the result column alone makes the network look healthy; the time lost only shows up if you measure it.

Why the browser was fine

Browsers and curl implement Happy Eyeballs (RFC 8305): if IPv6 doesn't answer within a short delay, they open an IPv4 connection in parallel and use whichever connects first. A broken IPv6 path is barely noticeable there. Programs that try one address at a time and wait out every timeout are the ones that freeze.

The same problem showed up before on HiNet at home. A Python live-stream checker hitting youtube.com stalled for about 168 seconds on every request: DNS returned 8 IPv6 addresses, each timing out after about 21 seconds, 8 × 21 = 168, and only then did IPv4 get a turn. curl fetched the same URL in 0.3 to 0.8 seconds, which nearly led to the conclusion that YouTube was throttling.

# Three commands to check it yourself

When a speed test looks fine but some program stalls, run these three steps in PowerShell to see whether it's the same cause.

1 — Does the domain have IPv6 addresses?

Resolve-DnsName gw.line.naver.jp -Type AAAA

If AAAA records come back, the program may try IPv6 first.

2 — Does IPv6 alone get through?

curl.exe -6 -m 15 -s -o NUL -w "%{time_connect}`n" https://www.google.com
curl.exe -4 -m 15 -s -o NUL -w "%{time_connect}`n" https://www.google.com

-4 answers instantly and -6 times out: IPv6 can't get out. Try a few sites such as Google and Cloudflare; if all of them time out, it isn't one site's problem.

3 — Is the program stuck on half-open connections?

Get-NetTCPConnection -State SynSent -OwningProcess (Get-Process LINE).Id

Remote addresses containing colons are connections stuck on IPv6.

# The fix and its cost

On the laptop, I removed IPv6 from the Wi-Fi adapter. Run as administrator: 

# Turn off
Disable-NetAdapterBinding -Name 'Wi-Fi' -ComponentID ms_tcpip6

# Turn back on later
Enable-NetAdapterBinding -Name 'Wi-Fi' -ComponentID ms_tcpip6

The setting belongs to the adapter, so it applies to every Wi-Fi network from now on and survives a reboot. The cost is losing IPv6 on networks where it does work; most services also offer IPv4, so day-to-day use feels the same. Get-NetAdapter lists adapter names; on a laptop it's usually Wi-Fi.

Microsoft's documentation, read afterwards, advises against removing IPv6 from adapters, because some Windows components use IPv6 internally and may misbehave. The recommended approach is to keep IPv6 and prefer IPv4 instead: set the registry value DisabledComponents to 0x20 and reboot. That effectively moves IPv4 above IPv6 in the precedence table; programs try IPv4 first and IPv6 stays available as a fallback. 

# Run as administrator, then reboot
$key = 'HKLM:\SYSTEM\CurrentControlSet\Services\Tcpip6\Parameters'
New-ItemProperty -Path $key -Name DisabledComponents `
    -PropertyType DWord -Value 0x20 -Force

Your own programs can be fixed without touching the system. In Python, wrap socket.getaddrinfo so it keeps only IPv4 results and falls back to the original list when there is no IPv4. That is how the live-stream checker above was fixed: requests went from 168 seconds to 0.15.

# After the fix

Turning IPv6 off stops the bleeding and leaves three things. First, this laptop now uses only IPv4 on every Wi-Fi network. Anything that needs IPv6, including IPv6-related development or testing, needs the restore command above first.

Second, the steadier long-term setup is Microsoft's prefer-IPv4 option. The hotspot's IPv6 stays broken, but programs go to IPv4 first and never touch it; on networks where IPv6 works, it is still there when needed.

Third, why IPv6 fails on the hotspot and on HiNet was not chased with the carriers this time. On a new network, run step 2 of the three commands once; if curl -6 answers instantly, that network's IPv6 works.

Next time a speed test looks fine but part of some program stalls, consider measuring how long its domain takes over IPv4 and over IPv6. It's much faster than reinstalling the program.
