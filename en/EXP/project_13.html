Final project for the National Taiwan University of Science and Technology (NTUST) Cloud Solution Architect training program, Spring 2026. The brief: build an LLM pipeline that extracts 10 electronic component datasheet PDFs into 11 structured fields. On top of the minimum bar, I used the Azure AI Foundry V1 API quota provided by the program to run a two-axis experiment (PDF extraction method × LLM model), pushing the V1 submission's 60.9% up to V2's 76.4%.

Heya

Every electronic component ships with an official spec sheet (called a datasheet) listing part number, operating temperature range, max voltage, pin count and similar parameters. Engineers consult these before picking a part or designing a circuit. The brief gives 10 such PDFs and asks for an automated pipeline: feed in a PDF, the AI extracts the spec parameters and fills 11 columns of an Excel sheet. The instructor prepared an answer key (specbook.xlsx) for cell-by-cell scoring. The minimum bar is "pipeline runs + submit one report" — pass.

# Task Spec

  • Input — 10 electronic component datasheet PDFs (diodes / rectifier bridges / transistor packages, all small components common in power circuits)
  • Output — 11 structured fields per PDF: Part Number (model code), Operating Temperature (working temperature range), Package Dimensions (component LxWxH in mm), PIN Number (pin count), I_O / I_F (output / forward current), V_F (forward voltage), V_RRM (max reverse voltage), I_R (reverse leakage current)
  • Scoring — byte-for-byte comparison against the specbook.xlsx answer key, per-field accuracy (11 columns × 10 PDFs = 110 answers, % = how many hit)
  • Minimum bar — pipeline runs end-to-end, one results report submitted, pass.

# Two-Axis Experiment Beyond the Minimum

The program supplied Azure AI Foundry V1 API quota this semester (free credits for running large AI models on Microsoft's cloud). Most students used it to get one model running for credit. I spent the quota on a systematic two-axis experiment instead:

Two-Axis Design

A pipeline like this has two critical parts: the tool that parses the PDF into text, plus the AI model that reads the text and extracts the fields. To find out which part has the biggest effect on accuracy, prepare several candidates for each and run every combination. 3 PDF extractors × 5 AI models = 15 runs, every run uses the same prompt, the same PDFs, the same answer key.

Classic controlled experiment: hold the rest constant, change one variable, measure the delta. V1 submission (the weakest qwen2.5:7b + pdfplumber) becomes the baseline. The other 14 combinations all compare against it, separating "swap the PDF tool" gains from "swap the AI model" gains.

Axis 1

PDF Extraction Method

  • pdfplumber (reads the PDF's embedded text layer, fast)
  • PyMuPDF / fitz (reads PDF vector objects, exposes character coordinates)
  • camelot-py (table-border detection, requires Ghostscript)

All three are common Python PDF extraction libraries, each strongest on a different PDF profile.

Axis 2

LLM Model

  • Local Ollama + qwen2.5:7b (V1 baseline, smallest and fastest)
  • Local Ollama + qwen2.5:14b (same family, one size up)
  • Azure GPT-4o (OpenAI flagship)
  • Azure Llama-4-Maverick (Meta open-source flagship)
  • Azure mistral-medium-2505 (Mistral mid-tier)

Local means the model weights are downloaded to a personal machine and run on its GPU, capped by VRAM. Cloud means calling Azure through an API to run flagship-tier models, consuming the program's quota.

# Iteration: Three Tracks Running in Parallel

From V1 submission to V2 overall best, three independent but interacting tracks. Every run gets archived into a dedicated subfolder under output/_archive/ (e.g. v1_qwen7b/, v2_iter6_qwen14b/, v2_pdfplumber_azure_gpt_4o/), so prior results stay intact.

Track 1: Prompt Redesign (12 Blind Design Decisions)

The V2 prompt follows a blind design principle — derived only from the 11 field names and general electronics datasheet domain knowledge, without referencing V1's actual outputs to reverse-fit. Blind design means: prompt rules are derived from the field definitions and datasheet domain conventions alone, never picked from V1's wrong answers to back-solve. This preserves generalization to unseen samples. The 12 decisions grouped by type:

Type Decision
Input handling D1 Part Number passed as input (already known before pipeline runs)
Few-shot guidance D2 ✓/✗ contrastive examples per field (edge case behavior of instruction-tuned models improves clearly over positive-only examples)
Disambiguation D3 Tj vs Tstg explicit warning, D10 V_RRM aliases (V_RWM / Working Peak)
Units & character rules D4 take MAX for L/W/H (not NOM/TYP), D5 mA→A / mV→V / inch→mm normalization, D7 use 、 as separator for multi-value strings, D9 μ→u character substitution, D12 preserve special characters in JSON keys
Multi-value D6 list every test condition for V_F / I_R (string type hints multi-value)
Domain knowledge injection D8 package → PIN mapping table (JEDEC / industry standard packages)
Self-validation D11 7-item self-check (covers high-frequency errors from D3-D9)

Track 2: PDF Extraction Method

Holding the same prompt and model constant, I rotated the PDF extraction backend to quantify how much each approach affects final accuracy:

  • pdfplumber — plain text layer, most stable on standard-format datasheets. V2 default.
  • PyMuPDF / fitz — vector object layer, parses pages with inline annotations and images more granularly, but overall accuracy ties with pdfplumber.
  • camelot-py — lattice mode detects table borders, requires Ghostscript. Strong on pure-table datasheets but trails pdfplumber overall.

Conclusion: across these 10 datasheet samples, the PDF axis spread is only 3.6% (see two-axis spread section below).

Track 3: Model Upgrade

Stage Combination Overall
V1 submission qwen2.5:7b + baseline prompt + pdfplumber 60.9%
V2 iter6 qwen2.5:7b + 12-rule prompt + post-process validators 61.8%
V2 local ceiling qwen2.5:14b + 12-rule prompt 64.5%

The main jump sits at "local qwen 14b → cloud GPT-4o / Mistral", a single step worth +12%.

Post-processing: validators.py

Even with the prompt redesign, around 10% of outputs still slip on format or logic edge cases. validators.py sits after the LLM and applies rule-based corrections:

  • Unit re-normalization (μ→u, mA→A, etc. as a second pass)
  • L/W/H forced to MAX
  • Multi-value field sorting + 、 separator recomposition
  • Missing JSON fields filled with null

V2 iter6 used the validator to push qwen2.5:7b from 60.9% to 61.8% (same model, post-processing only). The validator stayed in the pipeline after the model upgrades.

Spread = the gap between the highest and lowest scores across all combinations along a single axis. A larger spread means the variable has more leverage on the result.

The 4× ratio says: on this task, spending a fixed budget on a stronger model pays more than spending it on PDF preprocessing. Local qwen 14b → cloud GPT-4o in one step was +12%, the largest single jump in the entire experiment.

# Model Strength Specialization (per-PDF observation)

MBR15U150 is a multi-product datasheet (one PDF covering several model variants). It became a stress test for model capacity:

Model MBR15U150 hits (out of 11)
qwen2.5:7b (local) 1 / 11
qwen2.5:14b (local) 4 / 11
Llama-4-Maverick (Azure) 2 / 11(MoE active params smaller, regression)
mistral-medium-2505 (Azure) 6 / 11
GPT-4o (Azure) 7 / 11

The three cloud models each lead in different PDF profiles:

  • GPT-4o — multi-product datasheet leader (MBR15U150 7/11) and general electrical parameter leader (BAT750 10/11)
  • Llama-4-Maverick + mistral-medium-2505 — simple-table leaders (CD4148WTP both score 11/11)
  • mistral-medium-2505 — bridge rectifier leader (MSB30M 9/11)

If each PDF were assigned to whichever of the three cloud models scored highest on that specific document and their answers merged, the theoretical ceiling is 80.9%. The estimate requires the answer key to pick the best model per PDF, classifying it as an overfit ceiling (uses ground truth to pick the best). In actual use, with no answer key to compare against, the 80.9% is unreachable. The practical single-model ceiling stays at 76.4%.

# What 76.4% Means in Context

  • Against the course bar — the minimum requirement is "pipeline runs, pass," with no accuracy threshold. V2's 76.4% is 15.5 percentage points above the submission baseline of 60.9%.
  • Against task difficulty — 84 hits out of 110 answers. The datasheets come from different vendors and different eras, with substantial variance in field naming and table layout. The accuracy reflects cross-sample generalization on unseen PDFs.
  • Against future portability — the two-axis design transfers directly to similar tasks. For any "extract structured fields from unstructured documents" brief, running a two-axis matrix first gives a quantitative answer to where the budget should go.

# Stack

  • Language / main libraries — Python 3.11.5, pdfplumber, PyMuPDF, camelot-py, openpyxl, openai SDK, python-dotenv
  • Local inference — Ollama + qwen2.5:7b / 14b (Q4_K_M quantization)
  • Cloud inference — Azure AI Foundry V1 unified API (OpenAI-compatible endpoint, quota provided by the training program)
  • Inference config — temperature=0, num_ctx=16384, format=json
  • Table extraction support — Ghostscript 10.07.0 (camelot lattice mode dependency)
  • Architecture — pdf_extractor.py / llm_backend.py two abstraction layers, runtime combinations switchable through BACKEND × PDF_EXTRACTOR in .env
