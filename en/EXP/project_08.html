Claude Code Architecture, Part 1:
System Layers, Context Boundaries, and Caching

AI & Automation Context Engineering Prompt Caching
2026.03.12 BY GHOST_1010

Written from six months of going in circles with Claude Code. At first it looks like a ChatBot. Then the context turns noisy, the toolbelt grows but the output gets worse, and the rules I wrote stop being followed. That is a system architecture problem. To get Claude Code to behave, I had to understand the underlying six-layer structure and where the context boundaries actually sit.

Heya

Claude Code is Anthropic's command-line developer tool. After installation, the user chats with Claude in a local terminal, lets it read and write project files, run shell commands, and refactor across multiple files. Think "AI engineering assistant that knows how to use tools."

This and the next piece form a series, logging the underlying architecture observed after six months of heavy use. Context refers to all the information the AI has to read before each response — user rules, file contents, tool definitions. "Context turning noisy" means this information accumulates and interferes with itself, causing the AI to skip instructions and degrade in quality. The series breaks down the cause of this problem and the engineering solutions.

Core Loop and the Six Layers

Claude Code is a recurring agent loop:
collect context → act → verify → [done or back to collect]

When it stalls, the cause is almost always bad context or the lack of a verify / rollback step. Model intelligence is rarely the bottleneck. The cleanest way to reason about the system is to split it into six layers:

Layer Role
Context CLAUDE.md / rules / memory: tells Claude "what this is."
Action Tools / MCP: tells Claude "what it can do."
Methodology Skills: on-demand playbooks. Tells Claude "how to do it."
Control Hooks: enforce certain behaviors without relying on the model's judgment.
Isolation Subagents: contained workers for bounded autonomy.
Verification Verifiers: make output verifiable, reversible, auditable.

Strengthen any one layer in isolation and the whole thing tilts. A bloated CLAUDE.md poisons context. Too many tools wreck tool selection. Subagents everywhere cause state drift.

Boundaries: MCP / Tools / Skills / Hooks

CLAUDE.md & rules

Project-level contract and path-scoped rules.

Common misuse: dumping all team knowledge into one root file.

Tools & MCP

Give Claude access to external systems.

Common misuse: plugging in too many servers and choking the context.

Skills

On-demand workflows and method packages.

Common misuse: writing them like encyclopedias with no execution boundary.

Hooks & Subagents

Enforcement layer and isolated worker units.

Common misuse: replacing model judgment with hooks.

Context Engineering: the Real Constraint

Most people treat context as a capacity problem. The actual issue is signal-to-noise. Of 200K tokens, only a fraction is useful. MCP server tool definitions are the biggest hidden killer.

Layered loading strategy:
Always resident   → CLAUDE.md (project contract / build commands / hard rules)
Load by path      → rules (per-language / per-directory / per-filetype)
Load on demand    → Skills (workflows / domain knowledge)
Load in isolation → Subagents (heavy exploration / parallel research)
Never in context  → Hooks (deterministic scripts / audit / blockers)
The Compaction Trap and HANDOFF.md

Default compaction strips early tool output and file content first. Along with that, it strips the architectural decisions and the reasoning behind constraints.

  • Add explicit Compact Instructions in CLAUDE.md (must preserve architectural decisions, modified files, etc.).
  • A stronger move: before switching out of a complex session, have Claude write a HANDOFF.md covering progress, paths that worked, dead ends, and the next step. The next session loads it and resumes cleanly.

Prompt Caching: the Core of the Internals

Claude Code's entire architecture is shaped around prompt caching. High hit rate means lower cost and looser rate limits. Caching works on prefix matching, so ordering matters more than people think:

1. System Prompt (static) → 2. Tool Definitions (static) → 3. Chat History (dynamic) → 4. User Input (last)
Common ways to wreck the cache:
  • Putting dynamic content (like timestamps) into the system prompt. Dynamic info belongs in user messages, wrapped in a <system-reminder> tag.
  • Adding or removing tools mid-session, or reordering tool definitions non-deterministically.
  • Switching models mid-session. Caches are model-bound. Going from Opus to Haiku forces a full rebuild and ends up costing more. Hand off the task through a subagent instead.
