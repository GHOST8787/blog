The hardware is a Windows 11 laptop with an RTX 4060 Laptop GPU (8GB VRAM) and Ubuntu on WSL2. # Block by block

LLM inference engine — vLLM and Ollama

Deploying vLLM on WSL2 breaks down into seven steps: create a Python 3.12 virtual environment with uv (the machine defaults to 3.13, and vLLM only supports 3.9 through 3.12), install the vllm package, download the Qwen2.5-1.5B-Instruct weights locally (about 3GB), install the missing gcc (needed to compile the C extension), then start the service with vllm serve. Running vLLM in 8GB of VRAM requires --enforce-eager to switch off CUDA graphs, so vLLM computes on the fly instead of pre-reserving the whole of VRAM, at the cost of throughput. Once it was up, curl against the OpenAI-compatible /v1/chat/completions endpoint returned a Traditional Chinese reply, so the service was live.

Re-running the startup flow turned up two basic bash traps: @~ does not expand to the home path in some shell environments, so the full path or $HOME has to be written out; and the line-continuation \ in a multi-line command cannot be followed by whitespace, or the next line is treated as a new command.

Ollama is installed on the Windows side (0.30.11), with qwen2.5:1.5b already pulled (986MB, Q4_K_M quantisation), and a single ollama run qwen2.5:1.5b is enough to start chatting. It serves the same OpenAI-compatible API (localhost:11434), so moving a program from vLLM to Ollama only means swapping the URL and the model name, with no code changes.

Both sides ran the same Qwen2.5-1.5B over the same API, measured on two metrics: throughput (tok/s) and time to first token (TTFT). Results logged in MLflow:

Scenario Ollama 0.30 vLLM 0.24 Gap
Single-request throughput 47.3 tok/s 31.5 tok/s Ollama +50%
Total throughput, 8 concurrent requests 119.4 tok/s 102.4 tok/s Ollama +17%

On this 8GB laptop Ollama wins both. The reason is that vLLM is forced into enforce-eager mode, part of the VRAM is taken by WSL2 and other processes, and PagedAttention never gets to show its concurrency advantage. vLLM's strengths suit server-class GPUs (24GB and up), larger models and high-concurrency workloads.

What model size changes

A 1.5B-parameter model is too small: asked "what is vLLM", both sides got it wrong and invented features that do not exist, a textbook small-model hallucination. The engine decides how fast it runs and how many people it can serve; the model decides how accurate the answer is. Those two belong in separate columns. Ollama running faster is a performance result, vLLM answering wrongly is a model-capability limit, and the two sit at different layers.

Experiment tracking — MLflow

MLflow is installed on Windows (pip install mlflow) and holds the benchmark results above. Four runs are logged (vLLM single request, vLLM concurrent, Ollama single request, Ollama concurrent), mlflow ui opens the web interface, and the Compare page lays all four side by side on throughput and latency. The data lives in a SQLite file called mlflow.db, which the UI reads back automatically next time, so the results stay put.

One Windows pitfall: the MLflow web server starts several worker processes by default, Windows handles multiprocessing differently from Linux, and running it straight hangs. Capping it at a single process with --workers 1 fixed it.

Containerisation — Docker

Docker 29.1.3 is installed inside WSL2's Ubuntu, with the daemon managed by systemd. The practice route was: get docker run hello-world working to confirm the environment → write a small Flask API with a Dockerfile → docker build it into an image → docker run it as a container → curl the endpoint → clean up the container and the image.

Walking the whole flow once is walking "develop → package → deploy → verify" once. Stretch that route out and swap the small Flask API for a vLLM inference service, and it is the same set of moves used to deploy a real AI model.

Orchestration — K8s (k3s)

I started with kind (Kubernetes IN Docker) on WSL2 and ran into a structural docker-in-docker problem: dockerd inside WSL2 occasionally restarts itself, and the knock-on effect kills the cluster kind created outright; after the restart, creating the cgroup scope also fails and the cluster cannot be recovered. Someone has reported this on kind's GitHub issues, and it counts as a known limitation under WSL.

I switched to k3s (v1.36.2+k3s1), which installs from a single script. k3s is lightweight K8s running directly on Linux, which removes the layer of running K8s inside a Docker container inside WSL2. After practice, systemctl disable --now k3s shuts it down to save resources, and systemctl start k3s wakes it up next time.

One thing to watch with K8s NodePort: it binds to the node IP, so curl localhost:nodePort may not get through. The fix is to look up the virtual IP WSL2 assigned with hostname -I and use that IP instead.

Training framework — PyTorch

Installing vLLM already brought PyTorch along (torch 2.11 + CUDA 13.0, inside the vllm venv), so practising PyTorch needed nothing extra and ran in the same venv. I wrote a minimal GPU training script: linear regression y = 2x + 3 on CUDA, with loss falling from 148 to 0.26, confirming the GPU training path works.

Earlier coursework at NTUST MVC Lab had already used PyTorch for DQN (1.5 million steps, evaluation score 2990) and U-Net semantic segmentation (pixel accuracy 0.8505), which covered training loops, loss curves and optimisers. What this round confirmed is that the local GPU environment works under WSL2, and that the training and inference ends run fine on the same card.

Storage-side inference acceleration — aiDAPTIV+

aiDAPTIV+ is a product line from Phison Electronics that combines SSD storage with AI inference acceleration. Its design splits into three tiers: Cache handles staging and accelerating the KV cache during inference; Link covers distributed inference of a model across hosts; Pro moves part of the computation onto the SSD controller itself.

A few published figures: a configuration of two GPUs plus an 8TB SSD fine-tuning Llama 405B; SLC-grade dies rated at 100 DWPD to absorb the write volume of AI workloads; and Link 3.0 claiming to cut time to first token (TTFT) to a tenth.

Understanding vLLM's PagedAttention makes the design logic behind aiDAPTIV+ Cache clearer, since the two overlap in how they tackle KV cache management.
