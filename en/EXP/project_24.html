Building a Memory System to Block AI Hallucination
Three Gates, Checked Against the Same Reports on GitHub

AI & Automation Memory System Claude Code
2026.06.25 BY GHOST_1010

A common reliability problem with generative AI tools is that they output unverified content as fact: generating numbers that do not exist, claiming to have read a file they never opened. Putting these tools to real work calls for a layer of structure outside the model to intercept this kind of output. This piece records a memory and safeguard mechanism I built for the Claude Code I use day to day, checked against a cluster of reports about the same class of problem on GitHub in June 2026.

# The Three Situations Where It Fails Most Often

Start with three situations I actually ran into.

One: the data has not arrived, and it hands over a made-up number. I asked it to run several background searches at once; before any tool returned, it threw out a number as the conclusion. That number turned up in none of the search outputs afterward, filled in on its own before the data was complete.

Two: it says "not found" without looking. I asked it to confirm whether a previously saved memory file still existed; it ran no actual search and answered "does not exist" outright. The file sat in its original place.

Three: it proposes a rejected approach again. A plan already turned down earlier came back up, raised again without checking memory. This same error, re-pitching an old plan without checking memory, added up to 19 times.

What the three share is a confident tone over content that does not hold up, and they read smoothly and look normal, which makes them hard to catch at a glance after the fact. That is the trouble: it gets things wrong with confidence.

At first I tried to block this by writing rules. Plain-text rules carry limited force; the rules grew into the hundreds, and the same class of error repeated all the same. A rule is only a "description", and whether to follow it stays with the model, leaving the chain short of a step that would reliably stop it.

# My Approach: Stop It at the Moment It Errs

The mechanism has three layers, each matched to a concrete failure form.

  • Layer one, memory:
    File-based memory that preserves project progress and existing decisions across conversations, reducing repeated questions and lost information. Each fact lives in its own file, with its source attached.
  • Layer two, enforced checks (gates):
    Turning rules into checks that intercept before any action: no edits without checking memory first, output a diagnosis before editing, run a search before claiming "not found" or "does not exist". Among these, re-pitching a rejected plan without checking memory accumulated 19 errors of the same kind, and malformed commands accumulated 240, serving as the basis for setting up the matching checks.
  • Layer three, heartbeat:
    Checking whether the background automation is still alive. One time the background process responsible for writing memory quietly stopped, a whole stretch of data went unwritten, and it took quite a while to notice. So a heartbeat check went in: when the schedule misses its expected run, it reports on its own, ahead of finding out after the fact.

The three layers map to lost information, repeated errors, and silent failure. The actual interception points are four conditions: no memory check first, no diagnosis output first, no search before claiming "not found", and a heartbeat that misses its report. The moment any one condition holds, it stops right there.

# Others See This Too: The Same Situation on GitHub

In June 2026, a cluster of reports landed on the Claude Code project on GitHub, all about Opus 4.8. One recorded the model submitting a fabricated number before parallel tasks finished, with later confirmation that the number existed in no tool output. The official account of the overall hallucination rate is the lowest error rate across benchmarks, achieved by declining to answer uncertain questions; the parallel scenario above falls outside what that mechanism covers.

One of the reports is a developer's writeup: five failure modes distilled after two months of file-based memory. Below, each item on that list is checked against this mechanism, four of them already covered.

  • Rules are only descriptions; an enforced step is needed to intercept.
    Maps to the enforced checks in layer two.
  • Model output without a cited source gets carried forward as fact.
    Added this round: any external fact in memory must carry a source link, and what cannot cite one stays out.
  • History and current to-do state must be stored separately.
    The matching approach: one set of files holds history, another records only the current to-do.
  • Automation without a heartbeat fails silently.
    Maps to layer three, added recently.
  • Two files of the same name produce content drift.
    The matching approach: status follows the progress date, with file modification time for reference only.

Four of the five are covered by the existing mechanism; item two (unsourced output taken as fact) is the part added this round. This one sits among the kinds that file-based memory finds harder to intercept by hard mechanism, and it rests mainly on the rule "always attach a source when writing an external fact".

Control over hallucination comes mainly from structure outside the model. Whether the model's own behavior changes sits outside the user's control; the controllable part is whether an interception point exists at the moment the wrong output appears. An independent user's failure list, distilled after two months, overlaps heavily with this mechanism's design, and serves as one external check on the direction.
