Two Generations of a YouTube Digest Tool:
From n8n & Excel to a Vision Pipeline

AI & Automation Vision Pipeline Self-hosted
2026.05.18 BY GHOST_1010

Same requirement — turn a YouTube video into a Chinese digest I can actually keep — built twice with two completely different engineering approaches. This is a log of what changed between the two generations, what V1 left unsolved, and how V2 picked it up.

Heya

Originally built for personal use. V2 is now in open beta — feel free to try it, and please ping me if anything looks off. Drop a YouTube URL in, get back a structured Chinese digest a few minutes later (chapter jumps, key sections, takeaways worth keeping, original transcript, Excel archive). V1 used n8n (a visual node-based automation tool, similar to Zapier) wired to a GEMINI plain-text summarizer, writing output to Google Sheets. V2 was rebuilt end-to-end: web login plus URL paste, Claude Sonnet 4.6 reading transcript and frames together, output rendered as a shareable web page.

# The Problem: a 30-Minute Video, 5 Calls Worth Keeping

I watch a lot of YouTube. Replaying is inefficient. A 30-minute video might contain 5 actual takeaways. What I needed was a compressed digest I can archive directly:

  • Chapter jumping, so I can land on the exact moment a discussion happens
  • A structured summary of the whole video in a few paragraphs
  • Standalone takeaways that read on their own without rewatching
  • An Excel record so I can review what I watched each month

Both generations solve this. The difference is the engineering, and how deep that engineering can take the output.

# V1: n8n + Python + GEMINI + Excel

The first version stitched everything together with n8n. The structure was simple: 

manual URL drop → n8n webhook
                → Python (yt-dlp + transcript)
                → GEMINI generateContent
                → Google Sheets append

V1 in Detail

Aspect Implementation
Trigger Manually drop a URL into the n8n webhook
Digest engine GEMINI, text-only (reads transcript)
Output shape One-line summary + 5–8 bullet takeaways, written as a single Google Sheets row
Interface No dedicated UI. You read the Google Sheet.
Processing time 2–5 minutes per video, invisible until n8n finishes writing

What V1 Solved, What It Did Not

V1's value was making the loop work. Going from handwritten notes to automated bullets saved a lot of downstream time. A few things stayed unsolved:

  • All visual information was lost. Slides, whiteboards, screenshots, tables — the transcript only captures speech. For technical content, this matters the most.
  • No chapter jumping. To revisit a specific discussion later, the only option was ctrl+F on the transcript.
  • The summary layer was flat. One-line summary plus bullets works for fast scanning, but takeaways worth keeping deserve a more structured presentation.
  • Editing a prompt meant editing n8n. A visual workflow editor is convenient at the prototype stage. Version control, rollback, and code review are awkward.

# V2: Next.js + Firebase + Claude Vision + Local Worker

V2 rebuilt the architecture from scratch. From "an n8n workflow" to "web app + queue + local worker": 

web sign-in + paste URL
       ↓
[Vercel /api/videos/process] → Firestore status=queued
       ↑↓
[local worker daemon]                ← desktop runs 24h
   - yt-dlp + Whisper       → transcript + meta
   - Claude Call 1 (text)   → ChapterPlan + timestamps needing frames
   - extract_frames.py      → one frame per chapter
   - Firebase Storage upload
   - Claude Call 2 (text+vision) → StructuredVideoFull
       ↓
[Vercel /v/[id]] onSnapshot → renders the full report

Core Change: a 2-Call Vision Pipeline

The key engineering call in V2 was splitting the digest into two LLM calls instead of feeding the entire transcript to a model in one shot:

  • Call 1 (text-only): read the transcript, plan the chapter structure — minute ranges, topic per chapter, which timestamps need a visual lookup (a slide, a chart, a referenced image). Output is a ChapterPlan JSON.
  • Middle step: based on the timestamps from Call 1, extract the corresponding frames from the raw video with ffmpeg. One representative frame per chapter.
  • Call 2 (text + vision): feed the transcript, the chapter skeleton, and the frame images into the model. Output is the final structured digest — per-chapter highlights, standalone takeaways, frame descriptions, confidence notes.

The win here: vision tokens get paid for only where they earn their cost, instead of sampling a frame per second across the whole video. If Call 1 plans well, a 30-minute video needs about 5–8 frames total.

Metadata V2 Surfaces

The lower-right of the UI shows the processing record per video:

  • Transcription: whisper-large-v3
  • Digest: claude-sonnet-4-6
  • Cost: roughly 0.10–0.20 USD per video
  • Runtime: around 3 minutes

V1 hid all of this. Once cost and runtime are visible per video, decisions about rerunning or switching models become clearer.

# Mid-Build Pivot: Execution Location Is a Design Decision

During V2's build, "where the code runs" changed three times. This part is worth its own section, because it exposes a question that looks like "we'll figure it out later" and is not.

Attempt Where it ran Result
Try 1 Vercel function running yt-dlp directly Vercel runtime had no ffmpeg, Linux ARM binary mismatch. Failed to land.
Try 2 GitHub Actions runner All 3 e2e attempts failed. YouTube returned "Sign in to confirm you’re not a bot" — the datacenter IP range was flagged.
Try 3 Local worker daemon (home IP) Passed. Desktop runs 24h as a Firestore listener. The cloud queue hands work down to the home IP for execution.

The lesson compresses into one line:

For automation pipelines, "where the code runs" is a design decision tied to anti-bot policy. Some target sites restrict specific IP ranges. Pick the wrong hosting, and the architecture needs to be rebuilt.

The final V2 shape is cloud + local hybrid: auth, UI, and queue live on Vercel and Firebase. The actual download and processing stay on a home IP. This split was forced by YouTube's anti-bot rules, not designed in upfront.

# What's Next

V2's local worker is currently tied to one desktop. The next pivot is packaging the worker as a distributable installer, so the home IP stops being tied to a single machine. That moves the stack one step closer to "shareable" from "personal tool."

The real change from V1 to V2: treating "input dimensions, execution location, output layer" as three separate design decisions, each reconsidered. The model is one variable among the three.
